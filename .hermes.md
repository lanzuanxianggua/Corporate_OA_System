## Model
- Default model: `minimax-m3` (configured in ~/.hermes/config.yaml).
- This model is reasoning-enabled (emits `reasoning_content`); expect
  longer first-token latency but better planning on multi-step refactors.

## Behavior preferences for this project

- **Default toolset**: `terminal,file,web,delegation,todo,memory`.
  Hermes picks these by default but you can override with `-t`.
- **Terminal timeout**: 300s (already set in ~/.hermes/config.yaml) —
  enough for `mvn verify` on a single module. For full multi-module
  builds ask for `terminal.timeout=900` per-call if needed.
- **Maven invocations**: prefer `mvn -q -DskipTests package` for
  verification only. Run actual tests with `mvn verify -Dspring.profiles.active=ci`
  when MySQL+Redis are up (see CLAUDE.md testing section).
- **Long-running builds**: do not block on a full `mvn clean install`.
  Use background mode: ask Hermes to run as background process and poll.

## When to delegate (vs do it directly)

- Single-file edit, single grep, one terminal call: do it directly.
- Touching 3+ files in one refactor: delegate to a subagent with
  the goal and absolute file paths in `context`.
- Comparing approaches (e.g. "Spring AOP vs interceptor for X"):
  fan out to 2 subagents, synthesize.

## Conventions NOT already in CLAUDE.md

- Always run `pnpm typecheck` after touching `code/frontend/`.
- After backend changes, run the focused module tests:
  `mvn test -pl oa-<module> -Dspring.profiles.active=ci`
  (not the full suite, unless asked).
- The repo is currently in a detached-HEAD state with uncommitted
  changes in `code/backend/**`. Prefer surgical patches and avoid
  running `git reset --hard` or `git checkout --` without confirming.
- For multi-file work, suggest creating a branch first:
  `git switch -c feat/<name>` before delegating.
