# 自定义流程定义功能完整实现详解

## 整体功能概览

自定义流程定义让管理员可以通过**可视化配置界面**，为不同业务类型（请假、出差、报销等）定义各自的审批流程，**无需编写任何代码**。

```
用户使用流程：
┌─────────────┐   ┌──────────────┐   ┌─────────────┐   ┌──────────────┐
│ 管理员打开    │ → │ 配置审批步骤   │ → │ 设置分级审批  │ → │ 保存流程定义   │
│ 流程定义页面  │   │ (添加/排序)   │   │ (条件路由)   │   │ (自动校验)   │
└─────────────┘   └──────────────┘   └─────────────┘   └──────────────┘
                                                            ↓
┌─────────────┐   ┌──────────────┐   ┌─────────────┐
│ 员工提交申请  │ → │ 引擎按定义    │ → │ 自动分配审批人 │
│ (请假/报销等) │   │ 解析 JSON 图  │   │ 创建待办任务  │
└─────────────┘   └──────────────┘   └─────────────┘
```

### 3. 设计器状态管理

设计器内部维护两种状态：

```typescript
interface ApprovalStep {
    id: string;              // 唯一标识
    name: string;            // 步骤名称（如"部门主管审批"）
    assigneeType: string;    // 审批人类型：dept_manager | role | role_global | specific | role_chain
    assigneeValue: string;   // 审批人值（角色KEY 或 员工ID）
    multiEnabled: boolean;   // 是否启用多人审批
    multiType: "countersign" | "orsign";  // 会签/或签
    timeoutHours: number;    // 超时提醒时间
}

interface TierRule {
    id: string;
    field: string;           // 条件字段：amount | days | hours | level
    op: string;              // 运算符：> >= < <= == !=
    value: number;           // 阈值
    name: string;            // 追加审批节点名称
    assigneeType: string;    // 审批人类型
    assigneeValue: string;   // 审批人值
}
```

### 4. 审批人类型

| 类型 | 含义 | 界面选择 | 实际效果 |
|:---|:---|:---|:---|
| `dept_manager` | 直属上级 | 选择"直属上级" | 自动找发起人的部门负责人 |
| `role` | 本部门角色 | 选择"本部门角色"+ 选择角色 | 优先匹配同部门有该角色的人 |
| `role_global` | 全公司角色 | 选择"全公司角色"+ 选择角色 | 全公司范围内匹配有该角色的人 |
| `specific` | 指定员工 | 选择"指定员工"+ 搜索员工姓名 | 直接指定审批人 |
| `role_chain` | 角色链 | 选择"角色链"+ 输入 JSON 数组 | 从高级到低级逐一尝试 |

### 5. 三步模板快速创建

为简化操作，设计器提供了三种预设模板，一键生成通用流程：

```typescript
function applyTemplate(type: "standard" | "amount" | "duration") {
    if (type === "standard") {
        // 常规审批：部门主管 + 人事复核
        steps: [部门主管审批(dept_manager), 行政/人事复核(HR)]
    }
    if (type === "amount") {
        // 金额分级：审批节点 + 金额条件
        steps: [部门主管审批(dept_manager), 财务复核(FINANCE)]
        rules: [金额>5000→总监审批, 金额>50000→总经理审批]
    }
    if (type === "duration") {
        // 时长分级：审批节点 + 天数条件
        steps: [部门主管审批(dept_manager)]
        rules: [天数>7→总监审批]
    }
}
```

## 二、从可视化设计到 JSON 图结构

### 核心转换函数

当管理员在界面上点击每个输入框或按钮时，都会触发 `emitGraph()`，将当前 UI 状态实时转换为 JSON 图结构：

```typescript
function buildGraph() {
    const nodes: any[] = [
        { nodeId: "start", nodeType: "start", name: "开始", nodeName: "开始" },
    ];
    const edges: any[] = [];
    let previousNodeId = "start";

    // ① 遍历审批步骤 → 生成 approval 节点和边
    approvalSteps.value.forEach((step, index) => {
        const nodeId = step.id;
        const node = {
            nodeId,
            nodeType: "approval",
            name: step.name,
            nodeName: step.name,
            approvalMode: step.multiEnabled ? step.multiType : "single",
            assigneeRule: {
                type: step.assigneeType,
                value: assigneeValue,
                roleKey: ["role", "role_global"].includes(step.assigneeType) ? assigneeValue : undefined,
            },
            assigneeType: step.assigneeType,
            assigneeValue,
        };
        if (step.multiEnabled) node.multiType = step.multiType;
        if (step.timeoutHours > 0) {
            node.timeoutHours = step.timeoutHours;
            node.timeoutAction = "notify_only";
        }
        nodes.push(node);
        edges.push({ source: previousNodeId, target: nodeId });
        previousNodeId = nodeId;
    });

    // ② 如果有分级规则 → 生成 gateway 节点 + tier_approval 节点
    if (activeRules.length > 0) {
        const gatewayId = "gateway_tier_rules";
        nodes.push({
            nodeId: gatewayId,
            nodeType: "gateway",
            gatewayType: "exclusive",
            name: "分级审批判断",
            nodeName: "分级审批判断",
            branches: [],  // 分支条件
        });
        edges.push({ source: previousNodeId, target: gatewayId });
        previousNodeId = gatewayId;

        activeRules.forEach((rule, index) => {
            const nodeId = `tier_approval_${index + 1}`;
            branches.push({
                when: `${rule.field} ${rule.op} ${rule.value}`,  // 如 "amount > 5000"
                to: nodeId,
            });
            nodes.push({
                nodeId,
                nodeType: "approval",
                name: rule.name,
                assigneeType: rule.assigneeType,
                assigneeValue: assigneeValue,
            });
            edges.push({ source: gatewayId, target: nodeId });
            edges.push({ source: nodeId, target: "end" });
        });
    }

    // ③ 结束节点
    nodes.push({ nodeId: "end", nodeType: "end", name: "结束", nodeName: "结束" });
    edges.push({ source: previousNodeId, target: "end" });

    return { schemaVersion: 3, nodes, edges };
}
```

### 2. Service 保存逻辑

**文件**: `cn.oa.service.impl.WorkflowServiceImpl.saveDefinition()`

```java
@Override
@Transactional
public void saveDefinition(WfProcessDefinition definition) {
    // ① 校验 JSON 图结构
    WorkflowGraph graph = validateDefinition(definition.getNodeConfig());
    if (!graph.valid) {
        throw new BusinessException("流程定义校验失败: " + 
            graph.errors.stream()
                .map(error -> error.message)
                .collect(Collectors.joining("; ")));
    }

    // ② 生成流程标识（如未设置）
    if (definition.getProcessKey() == null) {
        definition.setProcessKey(definition.getProcessType() + "_process");
    }

    // ③ 如果是更新（已有 ID）→ 停用旧版本 → 创建新版本
    if (definition.getId() != null) {
        WfProcessDefinition existing = this.getById(definition.getId());
        existing.setStatus("1");              // 停用旧版本
        this.updateById(existing);

        definition.setId(null);               // 创建新版本
        definition.setVersion(existing.getVersion() + 1);
        definition.setStatus("0");
        definition.setCreateTime(LocalDateTime.now());
        deactivateActiveDefinitions(definition.getProcessType(), existing.getId());
        this.save(definition);
        return;
    }

    // ④ 新增 → 自动生成版本号
    definition.setVersion(nextDefinitionVersion(definition.getProcessType()));
    definition.setStatus("0");               // 默认激活
    deactivateActiveDefinitions(definition.getProcessType(), null);
    this.save(definition);
}
```

### 3. 版本控制策略

**版本管理**：

```
请假流程 v1 (已停用)
请假流程 v2 (已停用)  
请假流程 v3 (当前激活)
```

每次保存都会：
1. 旧版本 → 状态设为 `"1"`（停用）
2. 新版本 → 版本号 `+1`，状态设为 `"0"`（激活）
3. 使用中的流程实例不受影响（因为实例保存了 `snapshotNodeConfig` 快照）

```java
private void deactivateActiveDefinitions(String processType, Long excludeId) {
    // 停用同类型下所有已激活的定义（排除当前编辑的）
    LambdaQueryWrapper<WfProcessDefinition> wrapper = 
        eq(WfProcessDefinition::getProcessType, processType)
        .eq(WfProcessDefinition::getStatus, "0");
    if (excludeId != null) wrapper.ne(WfProcessDefinition::getId, excludeId);
    
    this.list(wrapper).forEach(def -> {
        def.setStatus("1");
        this.updateById(def);
    });
}
```

### 4. 在线校验功能

管理员在保存前可点击"校验"按钮进行实时验证：

**文件**: `cn.oa.controller.WorkflowController`

```java
@PostMapping("/definition/validate")
@RequireAdmin
public R<List<WorkflowValidationError>> validateDefinition(
        @RequestBody WfProcessDefinition definition) {
    WorkflowGraph graph = workflowService.validateDefinition(definition.getNodeConfig());
    return R.ok(graph.errors);
    // 返回错误列表，为空=校验通过
}
```

**校验规则（都在 `WorkflowRuntimeEngine.parseNodeConfig()` 中实现）**：

| 校验项 | 错误类型 | 说明 |
|:---|:---|:---|
| 节点不能为空 | `no_nodes` | 至少需要一个审批节点 |
| 必须有开始节点 | `no_start` | start 类型节点不能缺 |
| 只能有一个开始 | `multiple_start` | 多于一个 start 节点 |
| 必须有结束节点 | `no_end` | end 类型节点不能缺 |
| 节点ID不能重复 | `duplicate_node_id` | 两个节点使用相同 ID |
| 审批人不能为空 | `missing_assignee_type/value` | 每个审批节点必须指定审批人 |
| 不能有环路 | `cycle` | DFS 三色标记法检测环 |
| 必须可达 | `no_path_to_end` | 从开始无法到达结束 |
| 分支条件不能为空 | `missing_branch_condition` | 网关分支缺少 when 表达式 |

## 四、激活/停用流程定义

**文件**: `cn.oa.controller.WorkflowController`

**Service 实现**：

```java
@Override
@Transactional
public void activateDefinition(Long definitionId) {
    WfProcessDefinition definition = this.getById(definitionId);

    if ("0".equals(definition.getStatus())) {
        // 当前已激活 → 点击切换为停用
        definition.setStatus("1");
        this.updateById(definition);
        return;
    }

    // 当前未激活 → 先校验定义再激活
    WorkflowGraph graph = validateDefinition(definition.getNodeConfig());
    if (!graph.valid) {
        throw new BusinessException("流程定义校验失败: " + graph.errors...);
    }

    // 停用同类型的其他激活定义
    deactivateActiveDefinitions(definition.getProcessType(), definition.getId());
    // 激活当前定义
    definition.setStatus("0");
    this.updateById(definition);
}
```

## 八、完整示例：配置一个金额分级请假流程

### 操作步骤

```
① 管理员打开 /oa/workflow/definition → 点击"新增定义"

② 填写基本信息：
   流程名称：请假审批
   流程标识：leave_process  
   分类：请假 (leave)

③ 设计器操作：
   - 点击"金额分级"模板
   - 系统自动填充：
     审批步骤：部门主管审批 → 财务复核
     分级规则：金额>5000 → 总监审批
              金额>50000 → 总经理审批

④ 可选修改：
   - 修改"财务复核"的审批人为"全公司角色 → FINANCE"
   - 给"部门主管审批"添加超时提醒: 48小时

⑤ 点击"校验流程" → 校验通过

⑥ 点击"确定" → 保存成功

⑦ 员工提交 30000 元的报销申请 → 
   流程自动流转：部门主管审批 → 财务复核 → 总监审批(金额>5000匹配) → 归档
```

### 生成的 JSON 定义


### 实际运行效果

```
员工提交报销金额=30000

→ step1. 部门主管审批 (dept_manager)
     → 通过
→ step2. 财务复核 (FINANCE)
     → 通过
→ gateway: 金额 > 5000? → YES → 进入总监审批
→ step3. 总监审批 (DIRECTOR)
     → 通过
→ 归档 (end)
```

## 九、安全与权限设计

| 安全措施 | 实现 | 说明 |
|:---|:---|:---|
| **管理员权限** | `@RequireAdmin` | 只有 ADMIN 才能创建/编辑/激活流程定义 |
| **JSON 校验** | `validateDefinition()` | 保存前自动校验图结构，防止恶意构造 |
| **版本隔离** | 快照机制 | 修改定义不影响正在运行的流程实例 |
| **停用保护** | 停用同类型其他版本 | 确保同一类型只有一个激活定义 |

## 十、涉及技术点总结

| 技术 | 应用场景 |
|:---|:---|
| **Vue 3 + Composition API** | 可视化设计器的响应式状态管理 |
| **Element Plus** | `el-select` 下拉选择审批人、`el-switch` 多人审批开关、`el-input-number` 超时小时 |
| **v-model 双向绑定** | FlowDesigner 组件的 `modelValue` 与父表单的 `form.nodeConfig` 数据同步 |
| **Emit 通信** | `emitGraph()` 实时将 UI 状态转为 JSON 传给父组件 |
| **动态 JSON 生成** | `buildGraph()` 将步骤+规则转为 Schema v3 图结构 |
| **DFS 环检测** | `hasCycle()` 三色标记法校验图的合法性 |
| **版本号递增** | 每次编辑自动 +1，保留历史版本 |
| **快照模式** | `snapshotNodeConfig` 保存审批启动时的定义快照 |



 一、核心优点

  1. 无需改代码，业务人员可自行配置

  传统方式：如果要修改审批流程（比如金额超过 5000 需要总监审批），需要改 Java 代码、重新编译、部署、重启。

  // 传统硬编码方式
  if (amount > 5000) {
      // 找总监审批
      Long directorId = findDirector(initiatorId);
      createTask(directorId);
  } else {
      // 部门主管审批
      Long managerId = findManager(initiatorId);
      createTask(managerId);
  }
  // 改这个逻辑需要开发人员介入

  自定义流程：管理员在可视化设计器中拖拽配置，直接保存生效，零代码改动。

  2. 同一引擎支撑 7+ 种业务，大幅减少重复代码

  传统方式：7 种业务 × 各自写的审批逻辑 = 7 套代码
  自定义流程：7 种业务 × 同一 WorkflowService = 1 套代码

  // 所有业务的启动流程都调用同一个方法
  workflowService.startProcess("leave",    leaveId,    userId);   // 请假
  workflowService.startProcess("trip",     tripId,     userId);   // 出差
  workflowService.startProcess("expense",  expenseId,  userId);   // 报销
  workflowService.startProcess("purchase", purchaseId, userId);   // 采购
  workflowService.startProcess("overtime", overtimeId, userId);   // 加班
  workflowService.startProcess("outing",   outingId,   userId);   // 外出
  workflowService.startProcess("loan",     loanId,     userId);   // 借支

  3. 流程可运行时调整，不停机

  传统流程修改需要重新部署整个应用。自定义流程只需在界面上点击"新增版本"：

  传统：修改代码 → 编译 → 停服 → 部署 → 重启（影响所有用户）
  自定义：打开设计器 → 修改 → 保存 → 生效（不停机）

  而且已有正在审批的实例不受影响（快照隔离），新提交的单据才走新流程。

  4. 条件路由灵活组合

  4 维条件（金额、天数、小时数、角色级别）可任意组合，覆盖绝大多数 OA 场景：

  ┌──────────┬────────────────────────────┬───────────────────────────┐
  │   场景   │         条件表达式         │           效果            │
  ├──────────┼────────────────────────────┼───────────────────────────┤
  │ 金额分级 │ amount > 5000              │ 大额报销需总监审批        │
  ├──────────┼────────────────────────────┼───────────────────────────┤
  │ 天数分级 │ days >= 7                  │ 长假需总经理审批          │
  ├──────────┼────────────────────────────┼───────────────────────────┤
  │ 时长分级 │ hours > 8                  │ 加班超过 8 小时需更高审批 │
  ├──────────┼────────────────────────────┼───────────────────────────┤
  │ 复合条件 │ amount > 5000 && days >= 3 │ 金额和天数都超过才升级    │
  ├──────────┼────────────────────────────┼───────────────────────────┤
  │ 角色级别 │ initiator_level_match      │ 高管请假直接跳过低级审批  │
  └──────────┴────────────────────────────┴───────────────────────────┘

  5. 审批人策略灵活，适应组织变化

  ┌──────────┬──────────────────────┬────────────────────────────────┐
  │   策略   │       适用场景       │           组织变化后           │
  ├──────────┼──────────────────────┼────────────────────────────────┤
  │ 直属上级 │ 请假、外出等常规审批 │ 部门改组自动适配新领导         │
  ├──────────┼──────────────────────┼────────────────────────────────┤
  │ 角色     │ 按角色分配审批       │ 人员离职换人，重新分配角色即可 │
  ├──────────┼──────────────────────┼────────────────────────────────┤
  │ 角色链   │ 金额分级审批         │ 新增管理层级，只需修改链配置   │
  ├──────────┼──────────────────────┼────────────────────────────────┤
  │ 指定员工 │ 固定审批人           │ 人员变动需手动更新定义         │
  └──────────┴──────────────────────┴────────────────────────────────┘

  比如公司组织架构调整，部门经理换了人，只要角色没变，dept_manager 策略会自动找到新的部门经理，流程定义无需修改。

  6. 审批流程对用户透明

  用户提交申请时不知道也不关心背后是什么流程——引擎会自动路由。

  员工提交报销单 30000 元
    → 系统自动查流程定义
      → 解析条件：amount(30000) > 5000 → 匹配分级规则
        → 自动流转到总监审批
          → 员工只看到一个待办状态，不知道具体路由过程

  场景：公司调整采购审批规则，金额超过 3000 也需要总监审批

  传统硬编码方式：
  // 开发人员需要：
  // 1. 找到 PurchaseController 中调用审批的代码
  // 2. 修改条件判断逻辑
  // 3. 提交 PR → 走发布流程
  // 4. 申请停服窗口 → 部署 → 重启
  // 耗时：1-3 天（包含审批和部署流程）

  自定义流程方式：
  // 管理员操作（无需开发人员）：
  // 1. 打开 /oa/workflow/definition
  // 2. 找到采购审批 → 编辑
  // 3. 在分级规则中：金额>3000 → 总监审批
  // 4. 点击保存
  // 耗时：1 分钟

  ┌──────────────────────────────────────┬────────────────────┬────────────────────────────────┐
  │                 场景                 │ 推荐使用自定义流程 │              原因              │
  ├──────────────────────────────────────┼────────────────────┼────────────────────────────────┤
  │ 中小型企业，审批规则频繁变化         │         ✅         │ 无需开发介入，业务人员自主调整 │
  ├──────────────────────────────────────┼────────────────────┼────────────────────────────────┤
  │ 有多种审批类型（请假、报销、采购等） │         ✅         │ 一套引擎支撑所有类型           │
  ├──────────────────────────────────────┼────────────────────┼────────────────────────────────┤
  │ 组织架构经常调整                     │         ✅         │ 审批人策略自动适配新架构       │
  ├──────────────────────────────────────┼────────────────────┼────────────────────────────────┤
  │ 需要会签/或签等复杂审批模式          │         ✅         │ 设计器直接配置                 │
  ├──────────────────────────────────────┼────────────────────┼────────────────────────────────┤
  │ 仅 1-2 种简单审批，固定不变          │     ⚠️  也可用      │ 但自定义流程提供了更好的扩展性 │
  └──────────────────────────────────────┴────────────────────┴────────────────────────────────┘

  一句话总结：自定义流程的核心价值在于将审批规则的制定权从开发人员转移到了业务人员手中，让系统能快速适应业务变化，同时大幅减少重复代码。
