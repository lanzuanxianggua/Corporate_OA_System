# 自研工作流引擎完整实现详解

## 整体架构概览

本系统采用**自研轻量级工作流引擎**，而不是引入 Flowable/Camunda 等重量级方案。引擎支持 Schema v2/v3 的图结构定义，通过 JSON 配置化的方式实现审批流程的动态路由。

### 引擎核心组件

```
┌─────────────────────────────────────────────────────┐
│                   工作流引擎架构                       │
├─────────────────────────────────────────────────────┤
│                                                       │
│  ① 流程定义 (WfProcessDefinition)                    │
│     └── JSON 图结构（nodes + edges + conditions）     │
│                                                       │
│  ② 流程实例 (WfProcessInstance)                      │
│     └── 关联业务单据 + 运行时快照                      │
│                                                       │
│  ③ 任务 (WfTask)                                     │
│     └── 待办/已办/会签/或签/委派                       │
│                                                       │
│  ④ 运行时引擎 (WorkflowRuntimeEngine)                 │
│     └── 图解析 + 条件求值 + 路径推导                   │
│                                                       │
│  ⑤ 业务回调 (WorkflowCallbackDispatcher)              │
│     └── Spring Event 异步通知业务模块                   │
│                                                       │
└─────────────────────────────────────────────────────┘
```

### 完整请求链路（请假审批为例）

```
用户提交请假申请
  → 业务 Controller 保存请假单
    → 调用 WorkflowService.startProcess("leave", businessId, initiatorId)
      → 查最新流程定义 → 解析 JSON 图 → 条件路由过滤节点
        → 创建流程实例 → 创建第一个审批任务 → 分配审批人
          → 生成待办 → WebSocket 通知审批人

审批人处理任务
  → 调用 WorkflowService.handleTask(taskId, handlerId, status, remark)
    → 加分布式锁防并发 → 更新任务状态 → 插入审批记录
      → 如果是会签/或签 → 判断是否全部完成
        → 拒绝 → 调用 handleRejection → 回调业务模块
        → 通过 → 调用 advanceToNextNode → 进入下一节点
          → 所有节点完成 → 回调业务模块 (如扣减假期余额)
```

### 图解析过程

**文件**: `cn.oa.service.workflow.WorkflowRuntimeEngine.parseNodeConfig()`

解析器将 JSON 字符串转为内存中的 `WorkflowGraph` 对象：

```java
public WorkflowGraph parseNodeConfig(String nodeConfig) {
    // 1. 校验 JSON 合法性
    // 2. 提取 nodes 数组 → Map<nodeId, JSONObject>
    // 3. 提取 edges 数组 → 建立邻接表 Map<nodeId, List<edge>>
    // 4. 校验：
    //    - 必须有一个 start 节点和一个 end 节点
    //    - 所有审批节点必须有审批人配置
    //    - 检测环路（DFS + 三色标记法）
    //    - 从 start 出发可达所有节点
    //    - 必须有一条从 start 到 end 的路径
    // 5. 返回 WorkflowGraph (nodes + outgoing)
}
```

**校验错误类型**：

| 错误类型 | 检测逻辑 |
|:---|:---|
| `no_nodes` | nodes 数组为空 |
| `duplicate_node_id` | 两个节点 ID 相同 |
| `no_start` | 没有类型为 start 的节点 |
| `multiple_start` | 超过一个 start 节点 |
| `no_end` | 没有类型为 end 的节点 |
| `no_approval` | 没有任何审批节点 |
| `cycle` | 图存在有向环（三色 DFS 检测） |
| `no_path_to_end` | start 节点无法到达 end |
| `unreachable_node` | 存在无法从 start 到达的节点 |
| `missing_assignee_type` | 审批节点未配置审批人类型 |
| `missing_assignee_value` | 审批节点未配置审批人值 |

### 4 维分级条件路由

**文件**: `cn.oa.service.impl.WorkflowServiceImpl.resolveAssignee()`

```java
private Long resolveAssignee(String assigneeType, String assigneeValue, Long initiatorId) {
    return switch (assigneeType) {
        case "specific"              -> Long.valueOf(assigneeValue);          // 指定人
        case "role"                  -> resolveByRole(...);                    // 按角色（同部门优先）
        case "role_global"           -> resolveByRoleGlobal(...);              // 按角色（全局）
        case "dept_manager"          -> resolveDeptManager(...);               // 部门负责人
        case "role_chain"            -> resolveByRoleChain(...);               // 角色链
        case "initiator_level_match" -> resolveByInitiatorLevelMatch(...);     // 发起人级别匹配
        default                      -> Long.valueOf(assigneeValue);
    };
}
```

**4 维条件**：
| 维度 | 字段名 | 典型值 | 配置在流程节点上 |
|:---|:---|:---|:---|
| 金额 | `amount` | 5000, 50000 | `conditions: [{ field: "amount", operator: ">", value: 5000 }]` |
| 天数 | `days` | 3, 7 | `conditions: [{ field: "days", operator: ">=", value: 3 }]` |
| 小时 | `hours` | 8 | `conditions: [{ field: "hours", operator: ">", value: 8 }]` |
| 角色级别 | `role_level` | 3, 4 | 通过 `initiator_level_match` 解析 |

**不同审批人解析策略**：

| 策略 | 说明 | 使用场景 |
|:---|:---|:---|
| `specific` | 直接指定审批人ID | 固定审批流程 |
| `role` | 匹配有该角色的同部门员工 | 部门经理优先 |
| `role_global` | 匹配有该角色的任何员工 | 财务/HR 跨部门审批 |
| `role_chain` | 按角色链从高级到低级回溯 | 金额分级审批 |
| `dept_manager` | 逐级向上找部门负责人 | 请假审批 |
| `initiator_level_match` | 按发起人级别自动跳过低级别 | 高管审批省略中间环节 |

## 四、流程启动

**文件**: `cn.oa.service.impl.WorkflowServiceImpl.startProcess()`

```java
@Override
@Transactional
public WfProcessInstance startProcess(String businessType, Long businessId,
                                       Long initiatorId, Map<String, Object> conditionContext) {

    // ① 查最新启用的流程定义
    WfProcessDefinition definition = this.getOne(
        eq(WfProcessDefinition::getProcessType, businessType)
        .eq(WfProcessDefinition::getStatus, "0")
        .orderByDesc(WfProcessDefinition::getVersion)
        .last("LIMIT 1"));

    // ② 如果没找到流程定义 → 自动通过（无审批流）
    if (definition == null) {
        return autoApprove(businessType, businessId, initiatorId);
    }

    // ③ 解析 JSON → 条件过滤 → 得到可执行节点列表
    JSONArray materializedNodes = materializeExecutableNodes(definition, null, conditionContext);
    List<JSONObject> applicableNodes = filterApplicableNodes(materializedNodes, conditionContext);

    // ④ 如果没有可用的审批节点 → 自动通过
    if (applicableNodes.isEmpty()) return autoApprove(businessType, businessId, initiatorId);

    // ⑤ 创建流程实例（审批中状态）
    WfProcessInstance instance = new WfProcessInstance();
    instance.setProcessId(definition.getId());
    instance.setBusinessType(businessType);
    instance.setBusinessId(businessId);
    instance.setInitiatorId(initiatorId);
    instance.setStatus("0");                                 // 审批中
    instance.setSnapshotNodeConfig(definition.getNodeConfig());// 快照
    instance.setConditionContext(JSONUtil.toJsonStr(conditionContext)); // 条件上下文
    instanceMapper.insert(instance);

    // ⑥ 创建第一个审批节点的任务
    createTaskForNode(instance, applicableNodes.get(0), 0);

    return instance;
}
```

**核心设计决策——为什么需要快照？**

```
场景：用户 A 提交请假申请时，流程定义有 2 个审批节点
      用户 A 的审批进行到一半时，管理员修改了流程定义，增加了第 3 个节点
      如果没有快照，用户 A 的审批会突然多出一个没见过的节点

解决方案：启动时复制一份 nodeConfig 到 instance.snapshotNodeConfig
         后续审批全部使用快照中的定义，不受流程定义变更影响
```

### 多业务使用同一引擎

```
startProcess("leave",    leaveId,    userId)  → 请假流程
startProcess("trip",     tripId,     userId)  → 出差流程
startProcess("expense",  expenseId,  userId)  → 报销流程
startProcess("purchase", purchaseId, userId)  → 采购流程
startProcess("overtime", overtimeId, userId)  → 加班流程
```

## 五、任务处理

**文件**: `cn.oa.service.impl.WorkflowServiceImpl.handleTask()`

```java
@Override
@Transactional
public void handleTask(Long taskId, Long handlerId, Integer status, String remark) {

    // ① 参数校验
    if (status == 2 && (remark == null || remark.trim().isEmpty())) {
        throw new BusinessException("驳回时必须填写原因");
    }

    // ② 权限校验：审批人身份验证
    WfTask task = taskMapper.selectById(taskId);
    if (!task.getAssigneeId().equals(handlerId)) {
        // 检查委派关系：handlerId 是否是 task.assigneeId 的代理人
        // 检查管理员身份
        throw new BusinessException("无权处理此任务");
    }

    // ③ 分布式锁（Redis）——防并发
    // 关键场景：会签任务中多个审批人同时点击"通过"
    String lockKey = "lock:workflow:task:" + taskId;
    Boolean acquired = stringRedisTemplate.opsForValue()
        .setIfAbsent(lockKey, lockValue, 10, TimeUnit.SECONDS);
    if (!acquired) throw new BusinessException("系统繁忙，请稍后重试");

    // ④ 更新任务状态
    if (!"0".equals(task.getStatus())) throw new BusinessException("任务已处理");
    task.setStatus(String.valueOf(status));  // 1=通过 2=拒绝
    taskMapper.updateById(task);

    // ⑤ 记录审批记录（oa_approval_record）
    insertApprovalRecord(task, handlerId, status, remark);

    // ⑥ 会签/或签处理
    if (isMultiTask(task)) {
        handleMultiPersonApproval(task); // ↓ 见下方详解
    }

    // ⑦ 根据结果流转
    if (status == 2) {
        handleRejection(task, instance, isMultiTask);  // 拒绝 → 结束流程
    } else if (status == 1) {
        advanceToNextNode(task, instance, nodes, ctx); // 通过 → 下一节点
    }
}
```

### 会签与或签实现

**会签（countersign）**：**所有人**通过才算通过

```
任务创建时：生成 parentTask（逻辑分组）
            生成 childTask1 → assignee A
            生成 childTask2 → assignee B
            生成 childTask3 → assignee C

A 点击"通过" → childTask1.status=1 → 查 sibling: B、C 待处理 → 等待
B 点击"通过" → childTask2.status=1 → 查 sibling: C 待处理 → 等待
C 点击"通过" → childTask3.status=1 → 查 sibling: 无待处理 → **进入下一节点**
```

```java
// Countersign: 检查是否所有 sibling 都已通过
if ("countersign".equals(multiType)) {
    Long pendingCount = taskMapper.selectCount(
        eq(WfTask::getParentTaskId, parentId)
        .eq(WfTask::getStatus, "0"));

    if (pendingCount > 0) {
        return;  // 还有未处理的 sibling，等待
    }
    // 全部通过 → 继续流转到下一节点
}
```

**或签（orsign）**：**任意一人**通过即通过

```
任务创建时：生成 parentTask + childTask（同会签）

A 点击"通过" → childTask1.status=1 → 取消所有其他 childTask
             → B 的 childTask2.status=4(已取消)
             → C 的 childTask3.status=4(已取消)
             → **进入下一节点**
```

```java
// Orsign: 第一个通过的取消其他
if ("orsign".equals(multiType)) {
    List<WfTask> pendingSiblings = taskMapper.selectList(
        eq(WfTask::getParentTaskId, parentId)
        .eq(WfTask::getStatus, "0"));

    for (WfTask sibling : pendingSiblings) {
        sibling.setStatus("4"); // 取消
        sibling.setOpinion("或签已由其他审批人处理");
        taskMapper.updateById(sibling);
    }
    // → 继续流转到下一节点
}
```

## 六、节点推进与流程结束

### advanceToNextNode — 推进到下一节点

```java
private void advanceToNextNode(WfTask task, WfProcessInstance instance,
                                JSONArray nodes, Map<String, Object> ctx) {

    int currentIndex = runtimeIndex(task);
    instance.setCurrentNode(currentIndex);
    instanceMapper.updateById(instance);

    // 查找下一个符合条件的节点
    JSONObject nextNode = findNextApplicableNode(nodes, currentIndex, ctx);

    if (nextNode == null) {
        // ★ 没有下一个节点了 → 审批通过!
        instance.setStatus("1");
        instance.setEndTime(LocalDateTime.now());
        instanceMapper.updateById(instance);

        // 回调业务模块（如扣减假期余额）
        callbackDispatcher.onApproved(instance.getBusinessType(), instance.getBusinessId());
    } else {
        // 创建新节点的审批任务
        createTaskForNode(instance, nextNode, nextNode.getInt("runtimeIndex"));
    }
}
```

### handleRejection — 拒绝

```java
private void handleRejection(WfTask task, WfProcessInstance instance, boolean isMultiTask) {

    instance.setEndTime(LocalDateTime.now());
    instanceMapper.updateById(instance);
```

```java
    @Autowired
    private List<WorkflowCallback> callbacks;  // 自动注入所有回调实现

    public void onApproved(String businessType, Long businessId) {
        for (WorkflowCallback callback : callbacks) {
            try {
                callback.onApproved(businessType, businessId);
            } catch (Exception e) {
                log.error("Workflow callback error: {}", e.getMessage());
            }
        }
    }
}
```

**回调接口**：
```java
public interface WorkflowCallback {
    void onApproved(String businessType, Long businessId);
    void onRejected(String businessType, Long businessId);
    void onWithdrawn(String businessType, Long businessId);
}
```

**请假回调示例**：

```java
@Component
public class LeaveWorkflowCallback implements WorkflowCallback {

    @Autowired
    private LeaveService leaveService;
    @Autowired
    private AttendanceService attendanceService;

    @Override
    public void onApproved(String businessType, Long businessId) {
        if (!"leave".equals(businessType)) return;

        Leave leave = leaveService.getById(businessId);
        // ① 扣减假期余额
        leaveBalanceService.deduct(leave.getEmpId(), leave.getType(), leave.getDays());
        // ② 自动标记考勤为"请假"
        attendanceService.markLeaveAttendance(leave.getEmpId(), leave.getStartDate(), leave.getEndDate());
        // ③ 更新请假单状态
        leave.setStatus("approved");
        leaveService.updateById(leave);
    }

    @Override
    public void onRejected(String businessType, Long businessId) {
        if (!"leave".equals(businessType)) return;
        // 请假被拒，更新请假单状态为已拒绝
        Leave leave = leaveService.getById(businessId);
        leave.setStatus("rejected");
        leaveService.updateById(leave);
    }
}
```

## 九、Redis 在工作流中的使用场景

| 场景 | Redis 用法 | 代码 | 说明 |
|:---|:---|:---|:---|
| **分布式锁** | `SET key uuid NX EX 10` | `stringRedisTemplate.opsForValue().setIfAbsent(lockKey, value, 10, TimeUnit.SECONDS)` | 防止会签/或签并发处理导致重复推进节点 |
| **锁释放** | `GET key == uuid ? DEL key` | Redis Lua 或应用层比较后删除 | 只释放自己加的锁，不释放别人的锁 |
| **锁超时自动释放** | EX 10 秒 | Redis 自动过期 | 防止死锁（异常退出时锁自动释放） |
